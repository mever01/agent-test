# Архитектура и зависимости

Стрелки ниже показывают направление использования компонентов.

- HTTP → `app/api/` → `app/services/` или `app/agent/service.py`.
  Роутеры отвечают за HTTP-контракт, авторизацию через зависимости и
  перевод прикладных ошибок в HTTP-ответы. Прикладные операции размещай
  в сервисах.
- Сервисы → DAO, прикладные продюсеры и внешние клиенты.
  SQL, транзакции и работу с ORM размещай в `app/db/dao/`,
  ORM-модели — в `app/db/models/`. Общие DTO запросов и результатов,
  используемые несколькими модулями, размещай в `app/dto/`.
  Почтовые DTO находятся в `db_mail.py`, DTO индексации и поиска — в
  `rag.py`. Эти модули зависят от стандартной библиотеки и Pydantic.
  Схемы конкретного модуля, например agent, API или внешнего
  протокола, храни рядом с этим модулем.
- `app/agent/service.py` → граф → узлы → сервисы из `AgentContext`.
  Маршрутизацию храни в `graph.py`, состояние — в `state.py`,
  схемы инструментов и разбор их аргументов — в `tools.py`.
- RabbitMQ → `app/broker/rag/consumer.py` → `../app/services/rag/ingestion`.
  Индексация сохраняет подготовленные данные через DAO.
  Онлайн-поиск контекста обслуживает `../app/services/rag/retrieval`.
- В `app/services/rag/ingestion/` и `retrieval/` разделяй домены на
  пакеты `document/` и `email/`. Каждый пакет хранит свой `service.py`
  и хелперы. Общий алгоритм разбиения текста хранится в
  `ingestion/chunking.py`, очистка писем — в `ingestion/email/`.
  Общие DTO RAG находятся в `app/dto/rag.py`. Не загружай сервисы
  через `__init__.py`: схемы и хелперы должны импортироваться независимо.
- Циклы фоновой обработки, паузы и выбор заданий размещай в
  `app/workers/`. Цикл индексации писем находится в `email_indexing.py`,
  сборка зависимостей каждого воркера — в его точке входа `main()`.
  `document_indexing.py` обрабатывает очередь документов, `email_indexing.py`
  периодически выбирает письма. Сервисы обрабатывают отдельное задание
  и не запускают бесконечные циклы.
- `retrieval/email/` обслуживает гибридный поиск `search_emails`,
  `retrieval/document/` получает документы компании для ответа.
  Полные цепочки читаются через `ThreadService`, отдельные письма по ID
  для просмотра — через `RawEmailService`.
  API и агент вызывают отдельные сервисы и передают ID владельца явно.
  Саммари и векторы цепочек не создаются и не используются.
- `app/broker/rag/` → `core/broker/`. События, имена ресурсов и
  маршрутизацию RAG держи в `app/broker/rag/`. Общие механизмы RabbitMQ
  и логирования держи в `core/`. Импорты из `app/` в `core/` запрещены.
- Вызовы провайдеров LLM и эмбеддингов и преобразования их протоколов
  размещай в `app/external_api_clients/`. Настройки добавляй в
  подходящий модуль `app/configs/`, примеры переменных — в `.env.example`.
- Для Gmail используй один `GmailDAO` в
  `../app/db/dao/gmail/gmail.py`. DAO выполняет SQL в переданной
  сессии и преобразует ORM-объекты в DTO. Сервисы
  `app/services/gmail/` определяют переходы статусов, сроки,
  порядок операций и границы транзакций через `dao.transaction()`.
  Сетевые запросы выполняются после завершения транзакции.
- В `threads` и `raw_emails` используй универсальные `account_id`,
  `account_source` и внешние идентификаторы `external_thread_id` / `message_id`.
  `RawEmail.thread_id` ссылается на внутренний UUID цепочки. Привязка
  к аккаунту провайдера проверяется при записи; FK на `gmail_accounts`
  у цепочек отсутствует. В ограничениях уникальности и связи письма
  с цепочкой учитывай источник. Проверки доступа и получение адреса
  провайдера сосредоточены в `app/db/dao/query_helpers.py`;
  неизвестный источник не должен получать доступ по совпадению UUID.

Собирай зависимости API в `app/main.py` и `app/api/dependencies.py`,
зависимости воркеров — в `app/workers/document_indexing.py`
и `app/workers/email_indexing.py`. Передавай DAO, клиентов и продюсеры
через конструктор. Управляй временем
жизни общих ресурсов через lifespan и `AsyncExitStack`, как в
существующих точках входа. Сервисы, DAO и клиенты не должны
импортировать роутеры или точки входа. Избегай циклов импорта.
