# Контракты и проверки

- При изменении API, событий или результатов инструментов проверь
  производителей и потребителей. Сохраняй имена полей, HTTP-статусы,
  правила доступа и routing keys, если задача не требует изменить их.
  На текущем этапе разработки цепочку Alembic можно переписать,
  а данные локальной БД — пересоздать. При изменении схемы проверь
  `alembic upgrade head` на пустой БД и обнови сидинг и фикстуры,
  которые используют изменившиеся таблицы.
- При изменении операций записи проверь поведение при частичном отказе
  и повторе. Сохраняй дедупликацию черновиков по `operation_id`.
  Индексация писем выполняется автоматически после задержки
  из `RagWorkerConfig`.
  Сохраняй подтверждение сообщения после успешной обработки и
  существующую политику отклонения ошибочных сообщений.
- Сохраняй ролевые проверки и привязку сессии агента к владельцу.
  В графе проводи вызовы модели через `checked_chat`. Проверка canary
  должна предшествовать использованию ответа или аргументов
  инструмента. Сохраняй входную фильтрацию и маскирование PII на
  затронутых путях. В логах используй идентификаторы, этапы и типы
  ошибок. Не записывай секреты и сырые ответы модели.
- При правках RAG сохраняй разделение индексации и поиска, а также
  условия допуска данных к индексации. Используй
  [описание RAG](../docs/rag_architecture_and_limitations.md) и
  [описание защитных проверок](../docs/security.md) для сверки поведения.

Запускай ближайшие тесты из `tests/` через
`uv run --locked python -m pytest <путь-к-тесту>`. Для изменений
общих схем, сборки зависимостей или связей между компонентами запускай
полный набор через `uv run --locked python -m pytest`.
При готовом API-контейнере подходит `docker compose exec api pytest -v`.
При исправлении регрессии добавь тест, если существующие тесты её
не ловят. В отчёте указывай выполненные проверки и ограничения запуска.
