# Умышленные упрощения архитектуры и системные ограничения

Данный документ фиксирует инженерные компромиссы (trade-offs), допущенные при реализации проекта в рамках тестового задания, обоснование каждого решения и целевое состояние (Target Architecture) для промышленной эксплуатации (Production).

---

## 1. Умышленные архитектурные упрощения (Trade-offs)

Ниже приведена матрица упрощений:

### 1.1. Хранение сессий диалога и авторизации в оперативной памяти
* **Текущая реализация (MVP):**
  - Чекпоинты состояний LangGraph для механизмов уточнения (`clarify`, `interrupt`) сохраняются в `InMemorySaver`.
  - Авторизационные токены хранятся в словаре процесса API (`AuthService._sessions`) со временем жизни (TTL).
  - Защита от параллельного использования одного чекпоинта реализована локальным множеством `_resuming: set[UUID]`.
* **Инженерное обоснование:**
  - Исключение инфраструктурного оверхеда: запуск проекта не требует развёртывания и конфигурирования дополнительного кластера Redis / KeyDB.
  - Позволяет легко поднимать весь стек на локальных машинах с ограниченными ресурсами.
* **Целевое решение (Production Target):**
  - Использование `Redis` для хранения графовых чекпоинтов LangGraph.
  - Переход на внешний Redis Cluster для сессий авторизации с автоматическим TTL и распределённым кэшем.

---

### 1.2. Эвристический входной фильтр инъекций (Regex-based Inbound Guardrails)
* **Текущая реализация (MVP):**
  - Детекция Prompt Injection в `app/guardrails/inbound/injection_detector.py` выполнена на регулярных выражениях (`re.search` по списку `SUSPICIOUS_PATTERNS`).
* **Инженерное обоснование:**
  - Нулевая вычислительная задержка (0 ms latency) и 100% детерминированность.
  - Отсутствие дополнительной нагрузки на GPU/VRAM локального сервера моделей перед вызовом основного графа.
* **Целевое решение (Production Target):**
  - Двухслойный контур входной фильтрации:
    1. *Быстрый слой:* Regex-сигнатуры для отсечения тривиальных атак.
    2. *Интеллектуальный слой:* Специализированная легковесная классификационная модель (например, `DeBERTa-v3-Prompt-Injection` или `Llama Guard 3`) либо правила NeMo Guardrails для распознавания сложных семантических и многоязычных джейлбрейков.

---

### 1.3. Индексация писем через опрос PostgreSQL
* **Текущая реализация (MVP):**
  - Цикл в `app/workers/email_indexing.py` выбирает готовые письма из PostgreSQL
    после задержки из `RagWorkerConfig` и вызывает `EmailIngestionService`.
* **Инженерное обоснование:**
  - Состояние индексации хранится на письме, поэтому сбой оставляет его для
    следующей попытки. Перенос индексации в RabbitMQ для текущей нагрузки не требуется.
* **Целевое решение (Production Target):**
  - При переходе к нескольким воркерам потребуется координация захвата заданий.
    Если появится очередь индексации писем, публикацию можно связать с изменением
    письма через transactional outbox и сохранить проверку версии при обработке.

---

### 1.4. Последовательная обработка в RAG-консьюмерах (`prefetch_count=1`)
* **Текущая реализация (MVP):**
  - Воркер устанавливает `prefetch_count=1` для AMQP-канала и обрабатывает сообщения по очереди (`async for message in self._queue.iterator()`).
* **Инженерное обоснование:**
  - Защита локального окружения разработчика от исчерпания памяти: одновременный запуск десятков эмбеддинг- и LLM-запросов на локальной Ollama приводил бы к OOM или высоким задержкам ответа.
* **Целевое решение (Production Target):**
  - Асинхронная параллельная обработка через пул с ограничением параллелизма (`asyncio.Semaphore(concurrency_limit)`).
  - Воркер `document_indexing` можно масштабировать по длине очереди RabbitMQ.
    Для нескольких экземпляров `email_indexing` сначала потребуется координация
    захвата заданий из PostgreSQL.

---

### 1.5. Подстрочный перехват Canary Token (Exact Substring Matching)
* **Текущая реализация (MVP):**
  - Поиск маркера в тексте и JSON-аргументах основан на точном вхождении подстроки токена (включая рекурсивный обход декодированных структур и Unicode-экранирования).
* **Инженерное обоснование:**
  - Строгое соответствие требованиям ТЗ: детерминированный код без вызова дополнительных LLM-судей.
  - Гарантированное отсутствие False Positives (ложных срабатываний), блокирующих работу добросовестных менеджеров.
* **Целевое решение (Production Target):**
  - Комплексный контур защиты от эксфильтрации промпта:
    1. Точный Canary Token Interceptor (текущее решение).
    2. Honeypot-факты (фиктивные внутренние идентификаторы или секреты в промпте).
    3. Оценка семантической близости (Semantic Distance / Perplexity) ответа модели к тексту закрытого системного промпта.

## 2. Системные и эксплуатационные ограничения (System Limitations)

Ограничения, обусловленные выбранным скоупом предметной области и инфраструктурными границами:

| Параметр | Текущее ограничение | Влияние на систему | Способ обхода / масштабирования |
| :--- | :--- | :--- | :--- |
| **Модель коммуникации** | **1-на-1** (один менеджер и один клиент на тред) | Черновики адресуются ключевому клиенту цепочки. Сложные ветвящиеся треды со множеством контрагентов в копии (`CC`/`BCC`) не имеют матричной маршрутизации. | Доработка модели адресации: выделение списков участников `participants[]` и явный выбор адресата при вызове `create_draft`. |
| **Языковой скоуп** | **Русский и английский языки** | Полнотекстовый поиск PostgreSQL настроен под конфигурацию `'russian'`. Артикулы и латиница обрабатываются триграммами (`pg_trgm`). | Добавление мультиязычных FTS-конфигураций (`pg_catalog.english`) или гибридного поиска через OpenSearch/Elastic. |
| **Объём контекста агента** | **Запрос:** до 4000 симв.<br>**Письма:** до 20 посл.<br>**RAG:** top-5 чанков | Предотвращает переполнение контекстного окна локальной модели и деградацию качества (Lost in the Middle). | Использование длинноконтекстных моделей (32k–128k токенов) и алгоритмов реранкинга (Cross-Encoder / Cohere Rerank). |
| **Масштабирование API** | **Одиночный инстанс (Single Process)** | При наличии нескольких реплик API без общего хранилища чекпоинтов запросы с `continuation_id` могут попадать на разные ноды. | Подключение внешнего хранилища сессий (Redis / PostgresSaver) либо настройка Sticky Sessions на балансировщике (Nginx/Traefik). |
| **Фактологическая точность открытых LLM** | **Возможные мелкие галлюцинации локальных моделей** | Компактные открытые модели (`Qwen2.5:7b` / `3b`) могут смешивать детали регламентов (например, терминал доставки vs склад). | Переход на старшие модели (`Qwen2.5-72B`, `GPT-4o`, `Claude 3.5 Sonnet`) либо тонкая донастройка (SFT / DPO) под стиль компании. |
| **Срок жизни авторизации** | **Память процесса API (TTL = 3600 с)** | Перезапуск контейнера API инвалидирует текущие Bearer-токены менеджеров (требуется повторный логин в Swagger). | Сохранение сессионных токенов в PostgreSQL / Redis либо переход на асимметричные JWT (RS256) без сохранения состояния. |
