# План RAG-поиска по письмам

Дата подготовки — 17 ноября 2026 года.

## Состояние реализации

Реализованы индекс `email_chunks`, задержка из `RagWorkerConfig`,
объединение поиска внутри `search_emails`, выбор последней цепочки,
чтение актуальных сообщений и сохранение черновика с областью
доступа владельца. Основной граф подбирает документы компании.
Прежняя таблица сводок цепочек сохранена для экспериментального
baseline.

Начальные параметры реализации — cosine distance < 0,6,
RRF с константой 60 и до 100 кандидатов на ветку при выборе
последней переписки. Тема занимает до 300 символов в каждом
фрагменте, тело — до 1100, перекрытие тела — 200. Схема
`MailSnippet` дополнена датой последней активности цепочки,
заполняемой перед её выбором.

Проверки — 99 тестов с отдельной PostgreSQL, включая сквозной
сценарий поиска, чтения, документов и черновика. В сквозном тесте
ответы LLM и векторы заданы заранее. Планируемый benchmark
на 30 размеченных запросах требует отдельного выполнения.
Сравнительное качество реальных моделей этими тестами
не измерялось.

Миграции `002_rag_indexing` и `003_email_chunks` последовательно
переносят планирование на уровень писем. Существующие письма
получают время постановки при применении миграции.
API применяет миграции при запуске. Затем нужно перезапустить
Gmail-воркер и воркеры индексации с актуальным кодом.

Локальный запуск для текущего Compose-проекта:

```powershell
docker compose -p agent-test-clean --profile gmail up -d --build
docker compose -p agent-test-clean logs -f email_indexing document_indexing
```

Для ручного ускоренного прогона можно задать
`RAG_WORKER_INDEXING_DELAY_MINUTES=0` в `.env` и пересоздать
контейнер `email_indexing`. Значение по умолчанию — 30 минут.

## Решение для текущего проекта

Для основного пайплайна индексируем очищенный текст каждого письма. Длинное
письмо делится на фрагменты. Каждый результат хранит связь с исходным
письмом и цепочкой. После поиска можно загрузить соседние сообщения
цепочки для подготовки ответа.

По наблюдению пользователя в импортированном ящике 372 письма,
и только четыре цепочки содержат больше одного сообщения. Это
характеристика текущей выборки, которую при сравнении нужно заново
зафиксировать SQL-запросом. Число писем в цепочке не определяет допуск
к индексации.

Индексация запускается автоматически через 30 минут после сохранения
нового или изменённого письма. Задержка настраивается через
`RagWorkerConfig.indexing_delay_minutes` и переменную
`RAG_WORKER_INDEXING_DELAY_MINUTES=30`. Для каждого письма отсчёт
идёт от его собственного изменения в PostgreSQL. Новое сообщение
в цепочке получает собственный срок. Повторная синхронизация
неизменившихся данных срок не сдвигает.

Цепочки хранятся в `threads`, а `read_thread` читает их сообщения
из PostgreSQL. Векторный индекс сводок цепочек исключается из основного
пайплайна. Суммаризация выполняется по запросу пользователя.
Размер фрагмента и параметры объединения поиска проверяются
на локальной выборке.

## Согласованный сценарий из ТЗ

Запрос пользователя — «Найди последнюю переписку с клиентом по
проекту X, перечисли согласованные сроки и подготовь черновик ответа
на его последнее письмо с учётом условий поставки».

1. `search_emails` получает кандидатов полнотекстовым поиском
   с существующим GIN-индексом и семантическим поиском по
   `email_chunks`. В обеих ветках действуют фильтры владельца,
   участника и дат. Кандидаты объединяются, результаты нескольких
   фрагментов сворачиваются по `email_id`.
2. Код группирует подходящие письма по `thread_id`. Для выбора
   последней переписки сравнивает дату последнего сообщения
   каждой подходящей цепочки, включая сообщения без упоминания
   проекта. Семантическая близость определяет релевантность
   кандидатов. При неоднозначности проекта или клиента агент
   уточняет запрос. Ограничение числа кандидатов учитывается
   при заявлении о полноте поиска.
3. `read_thread` читает полную выбранную цепочку в хронологическом
   порядке из PostgreSQL. Агент выделяет подтверждённые сроки,
   учитывает последующие изменения и определяет последнее
   входящее письмо клиента. Полнота исходных данных не зависит
   от того, успели ли построиться эмбеддинги последних сообщений.
4. Внутренний retrieval-сервис подбирает документы об условиях
   поставки. Граф передаёт их вместе с перепиской на подготовку
   ответа через существующий узел `read_and_retrieve`.
5. `create_draft` сохраняет черновик с выбранным `thread_id`,
   проверенным получателем, темой и текстом. Результат содержит
   согласованные сроки, ссылки на исходные письма и документы,
   а также `draft_id`. Права владельца проверяются и при записи.

Назначение трёх инструментов сохраняется. Семантический поиск
добавляется внутрь `search_emails`. Полнотекстовый поиск и чтение
цепочки работают по импортированным данным сразу. Задержка 30 минут
относится к появлению письма в семантическом индексе.

## Похожие реализации и измерения

### mailrag

Открытый проект использует поиск сообщений с последующим расширением
до цепочки, dense/sparse-поиск и RRF. В демонстрации на 1 200 письмах
Enron и 99 вопросах к отдельным сообщениям автор приводит Recall@5
60,6% для обычного индекса и 73,7% для индекса с контекстом цепочки.
Это +13,1 процентного пункта. На другом публичном тесте из 360 запросов
и 2 000 документов Enron-QA указаны 94,4% для dense и 97,5%
для dense + learned-sparse.

Метрики опубликованы автором в README и снабжены ссылками на наборы
и команды запуска. В этой работе тесты проекта не воспроизводились.
Вариант с контекстом включает дополнительную обработку, а sparse-модель
отличается от PostgreSQL FTS. Результат поддерживает проверку поиска
по письмам и расширения цепочки. Его численные значения требуют
отдельного воспроизведения на нашем корпусе.
[Реализация и опубликованные результаты mailrag](https://github.com/fmasi/mailrag)

### Gmail Email Event Finder

Проект `AshirRashid/gmail-rag` индексирует очищенное письмо целиком
через локальную `BAAI/bge-base-en-v1.5`, хранит эмбеддинги по ID
сообщения в ChromaDB и ищет события, встречи и сроки. В README
заявлены semantic Recall@5 = 0,849, BM25 Recall@5 = 0,688 и
медианная задержка запроса 60,7 мс.

Это авторские измерения узкого поиска событий. Реализация пропускает
ответы и индексирует первое письмо цепочки. Для нашего сервиса нужно
обрабатывать все сообщения, поскольку ответ может менять условия.
Детальный отчёт `eval/README.md` при подготовке документа получить
не удалось. Размер теста, оборудование и метод разметки по доступному
README не установлены. Поэтому эти числа служат примером отчётности,
а обещание аналогичной скорости или полноты поиска требует измерений.
[Реализация и README Gmail Event Finder](https://github.com/AshirRashid/gmail-rag)

### Nylas

Практическое руководство описывает два сценария — работу с известной
цепочкой и поиск по всему ящику. Для второго предлагаются эмбеддинги
сниппетов с загрузкой полных сообщений после отбора. Очистка подписей
и цитируемых ответов выполняется перед подготовкой контекста.
Руководство полезно как описание потока данных. Для нашего случая
первые символы письма могут не содержать искомый факт, поэтому
предлагается проверить фрагменты полного очищенного текста.
[Руководство Nylas по почтовому контексту](https://developer.nylas.com/docs/cookbook/ai/email-context-for-llm/)

### Anthropic Contextual Retrieval

Авторы измеряли top-20 retrieval failure rate на своих корпусах.
Contextual embeddings вместе с contextual BM25 снизили показатель
с 5,7% до 2,9%, что составляет 49% относительного уменьшения ошибок.
Это исследование общего RAG, и контекст для фрагментов создаётся
дополнительными LLM-вызовами. Для тестового задания достаточно
проверить пользу текстового поиска вместе с векторным на уже имеющемся
PostgreSQL. Непосредственный перенос опубликованного процента
на письма и наш стек требует нового эксперимента.
[Методика и результаты Anthropic](https://www.anthropic.com/research/contextual-retrieval)

## Сравниваемые варианты

| Вариант | Единица поиска | Расход при индексации | Что проверяем |
| --- | --- | --- | --- |
| Текущая сводка треда | Одна сводка цепочки | LLM-суммаризация и эмбеддинг | Сохраняются ли конкретные даты, суммы и условия |
| Очищенное письмо | Письмо или его фрагмент | Эмбеддинги очищенного текста | Находится ли конкретное письмо, включая одиночное |
| Письмо и расширение контекста | То же письмо, затем сообщения цепочки | Те же эмбеддинги, больше чтения при ответе | Достаточен ли контекст для понимания коротких ответов |

Первый вариант используется только как baseline для эксперимента.
Основной пайплайн использует индекс писем и чтение выбранной цепочки.
Внутри `search_emails` объединяются полнотекстовый и векторный поиск
с дедупликацией результатов. RRF можно использовать как простой
способ объединения ранжированных списков. PostgreSQL FTS
остаётся собственной лексической реализацией проекта, отличающейся
от BM25 и learned-sparse моделей из источников.

## Этап 1. Данные и конфигурация

1. Сохранить `RagWorkerConfig` с одним действующим параметром
   задержки. Новые параметры добавлять по мере реализации поведения.
2. Добавить `email_chunks` с полями `id`, `email_id → raw_emails.id`,
   `chunk_index`, `content`, `embedding`. Уникальность
   `(email_id, chunk_index)`, удаление фрагментов при удалении письма.
   Размер вектора согласовать с текущими 1 024 измерениями модели.
   Принадлежность владельцу выводится через письмо, тред и аккаунт.
3. В `raw_emails` добавить время последнего изменения содержимого
   и время версии, для которой успешно построен индекс.
   Обновлять первое поле при фактическом изменении индексируемых
   данных. Идентификаторы и исходный текст остаются в `raw_emails`.
4. Адаптировать текущую незавершённую реализацию отложенных сводок
   тредов под письма. Поля `rag_updated_at` и `rag_indexed_at` треда,
   добавленные в рабочем diff, перенести на подходящий уровень.
   Проверить фактически применённую ревизию перед изменением миграций.
   Уже импортированным письмам назначить время постановки при миграции.
   Время получения письма из Gmail не используется как время импорта.

Критерий завершения — одиночные письма и ответы имеют одинаковую
схему индексации, а повторный импорт сохраняет ранее рассчитанный срок.

## Этап 2. Очистка и фрагменты

1. Переиспользовать `clean_email_body`, проверив его поведение на
   пересылках. Сейчас cleaner обрывает текст на заголовке пересылки,
   хотя именно пересланный блок может содержать нужный факт.
   Сохранять такой блок, если иначе содержимое теряется.
2. Готовить текст из темы и очищенного тела. Служебные поля
   отправителя, получателя и даты использовать как метаданные
   фильтрации и контекста ответа.
3. Короткое письмо индексировать одним фрагментом. Длинное делить
   по абзацам с жёстким ограничением длины. Начальный размер —
   1 500 символов и перекрытие 200 символов, как отправная точка
   для переиспользования существующего чанкинга. Проверить, что
   добавление темы укладывается в лимит входа embedding-модели.
   Количество символов не приравнивать к количеству токенов.
4. Сохранять короткие ответы вроде «Да, согласовано». При извлечении
   дополнять их контекстом цепочки. Если очистка оставила пустое тело,
   индексировать содержательную тему либо явно отмечать письмо как
   обработанное без фрагментов. Пустое письмо не должно постоянно
   возвращаться в очередь.

Критерий завершения — известный факт из тела и осмысленный пересланный
блок доступны поиску, а цитаты не размножаются во всех ответах.

## Этап 3. Фоновая индексация

1. Запускать опрос PostgreSQL отдельным воркером `email_indexing`.
   После первого успешного Gmail-импорта выбирать письма, у которых
   прошла задержка и текущая версия ещё не проиндексирована.
2. Последовательно обрабатывать небольшие пачки. Генерация эмбеддингов
   использует существующий клиент. Успешный проход не вызывает
   LLM-суммаризацию.
3. До обработки запомнить версию письма и поколение подключения.
   Перед записью проверить, что письмо не изменилось и аккаунт
   по-прежнему доступен. Фрагменты заменить и зафиксировать версию
   в одной транзакции. При ошибке оставить письмо для следующего
   прохода. Поддерживать один экземпляр индексирующего воркера
   в тестовом окружении.
4. Убрать автоматическую суммаризацию и векторизацию цепочек
   из основного пути, включая запуск по `thread_closed`.
   Проверить связанные сидинг, тесты и документацию. Автоматическая
   обработка писем запускается по времени после импорта.

Критерии завершения — одинаковые данные повторно не расходуют
embedding-вызовы, сбой не помечает письмо готовым, а новая версия
не получает устаревшие фрагменты.

## Этап 4. Поиск и контекст агента

1. Добавить репозиторий поиска по `email_chunks` и модели запросов
   и результатов. В результат включить ID письма, ID треда, дату
   и найденный текст. В `RagChunk` добавить тип источника
   `email_chunk` и `email_id`.
   Подключить его внутри `search_emails` совместно с текущим
   полнотекстовым поиском и вернуть прежние поля `MailSnippet`.
2. Передавать владельца из HTTP-сессии через сервис агента к
   поиску. Ограничивать SQL по владельцу и доступному подключению
   до сортировки и LIMIT. Та же проверка применяется при загрузке
   исходного письма и цепочки.
3. Для обычного поиска выдавать top-5 писем, сворачивая несколько
   фрагментов одного письма. Для сценария последней переписки
   сначала отобрать релевантные цепочки и сравнить дату последнего
   сообщения в каждой. Затем вызвать `read_thread` для выбранной
   цепочки. Ограничивать итоговый контекст возможностями модели,
   сохраняя сообщения, подтверждающие сроки и изменения условий.
4. Источниками ответа служат конкретные письма. Порядок дат
   сохраняется, чтобы позднее изменение условий не смешивалось
   с первоначальной договорённостью.
5. Включить Gmail-письма в поиск и чтение агента и разрешить
   `create_draft` владельцу выбранного аккаунта. Сейчас эти пути
   ограничены учебными данными. Передавать область доступа через
   `AgentContext`, сервисы и репозитории.
6. Сохранить inbound/outbound guardrails на пути агента.
   При отключении аккаунта его фрагменты исключаются из поиска.
   Текущий Gmail-опрос по дате не отслеживает удаления. Для полного
   соответствия индекса ящику понадобится отдельная сверка
   или переход на историю Gmail.

Критерий завершения — поиск и развёртывание цепочки не раскрывают
письма другого менеджера, а ответ ссылается на исходные сообщения.

## Этап 5. Небольшой локальный benchmark

Подготовить 30 запросов с ручной разметкой релевантных email ID
и ожидаемых фактов. Письма владельца можно использовать локально,
а в репозиторий положить обезличенные фикстуры.
Включить перефразирование, точные номера и даты, вопрос к пересылке,
короткий ответ и вопросы, требующие нескольких писем цепочки.
Для редких цепочек дополнить тестовый корпус синтетическими
сценариями с явно заданными фактами.

Сравнить на одном снимке данных и одной embedding-модели:

- PostgreSQL FTS как доступную базовую линию.
- Текущие сводки цепочек.
- Очищенные письма и фрагменты.
- Фрагменты с расширением контекста цепочки при формировании ответа.
- FTS + векторный поиск как согласованный рабочий вариант.

Для сводок тредов заранее отметить релевантные thread ID.
Сравнивать покрытие исходных email ID через сводку нужно отдельно,
поскольку одна цепочка может содержать много писем. Отчёт включает
метрики поиска писем и метрики покрытия доказательств в итоговом
контексте.

| Метрика | Определение |
| --- | --- |
| Recall@5 | Для каждого запроса доля размеченных релевантных писем среди пяти уникальных найденных писем, затем среднее по запросам |
| Hit@5 | Доля запросов, для которых найдено хотя бы одно релевантное письмо |
| MRR@5 | Среднее обратного ранга первого релевантного письма в top-5, ноль при промахе |
| Полнота контекста | Доля всех необходимых email ID, попавших в контекст генерации |
| Ответ с источником | Число ответов с правильным фактом и корректной ссылкой на письмо |
| Задержка p50/p95 | Отдельно поиск и полный ответ, с фиксацией прогрева и оборудования |
| Расход индексации | Время, число эмбеддингов, размер входного текста и число LLM-вызовов |

В каждой ячейке отчёта указывать абсолютное число успешных запросов
и долю. На 30 запросах один исход меняет Hit@5 примерно на
3,3 процентного пункта, поэтому небольшие отличия проверять разбором
конкретных запросов. Отдельно вывести результаты реальных писем
и синтетических цепочек.

Условия сравнения фиксировать вместе с результатом — размер корпуса,
распределение длин, модель, настройки фрагментов, top-k и состав
контекста. Стоимость локального запуска описывать временем и ресурсами.
Платёж внешнему API может равняться нулю при наличии вычислительных затрат.

## Проверки и готовность к демонстрации

- Миграция применяется к тестовой PostgreSQL, существующий Gmail-импорт
  продолжает работать.
- Письмо добавлено в 12:00 — при задержке 30 минут оно доступно
  индексации после 12:30. Повторное чтение из Gmail в 12:10
  не меняет этот срок. Для ручной проверки допустима задержка 0.
- Вторая индексация без изменений делает ноль embedding-вызовов.
  Новое письмо в цепочке приводит к обработке этого письма.
- При отказе модели предыдущий индекс остаётся согласованным,
  а неуспешная версия обрабатывается повторно.
- Тесты проверяют чтение и векторный поиск от второго владельца,
  отключение подключения и изменение письма во время индексации.
- Демонстрация включает одиночное письмо, смысловой запрос,
  точный идентификатор и цепочку с изменённой договорённостью.
- Сквозной тест воспроизводит запрос из ТЗ. В двух цепочках проекта
  последнее письмо одной цепочки не содержит название проекта,
  но делает её самой свежей. Агент выбирает её, учитывает изменение
  срока, отвечает на последнее входящее письмо клиента и сохраняет
  черновик с условиями поставки из документа. Вторая проверка
  выполняется до индексации нового письма в уже найденной цепочке.
- Финальный отчёт показывает результаты локального benchmark.
  Утверждение о лучшем варианте делается по полученным данным.

## Границы первой реализации

Сохранить PostgreSQL/pgvector и существующие клиенты.
Предложенный объём включает один новый тип индексируемого источника,
одну задержку в `RagWorkerConfig` и подгрузку контекста цепочки.
Реранкер, автоматическая LLM-классификация ценности письма,
дневной бюджет токенов и генерация контекста для каждого фрагмента
могут добавляться при наличии измеренной проблемы.

Связанные документы — [план Gmail](gmail_integration_plan.md) и
[текущая архитектура RAG](rag_architecture_and_limitations.md).
