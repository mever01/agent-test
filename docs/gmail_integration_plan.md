# План интеграции Gmail

## Цель первой версии

Менеджер создаёт именованный Gmail-аккаунт в сервисе, вводит параметры
OAuth-клиента и подтверждает доступ в Google. Отдельный воркер читает
подключённый ящик и сохраняет цепочки Gmail в `threads`, а их
сообщения — в существующую таблицу `raw_emails`. На фронте владелец видит
состояние подключения, время последнего успешного обмена и ошибки,
требующие его действий.

Предлагаемый объём импорта — входящие, отправленные и архивные письма
без Gmail-черновиков, спама и корзины. Вложения, отправка писем
и запись в Gmail остаются за рамками первой версии. Поиск и просмотр
импортированной почты доступны владельцу через HTTP. Подключение этих
писем к агенту, эмбеддингам и RAG — отдельный этап.

## Что уже есть в проекте

- `Thread` и `RawEmail` используют внутренние UUID. Тред хранит
  прикладной статус, письмо — одного отправителя, одного получателя,
  дату, тему и текст. PostgreSQL строит полнотекстовый индекс из темы
  и тела. Текущий `MailRepository.upsert_thread` обновляет статус,
  поэтому для Gmail нужен отдельный путь записи.
  [Модели БД](../app/db/models) ·
  [Репозиторий писем](../app/db/dao/mail_repository.py)
- HTTP-роуты проверяют роль manager/admin, но поиск, чтение и
  закрытие тредов сейчас не фильтруются по владельцу. Сессия агента
  знает пользователя, однако её вызовы почтового сервиса используют
  общий репозиторий. При чтении треда агент передаёт часть текста
  в запрос эмбеддингов, а существующий RAG-воркер обрабатывает
  событие закрытия.
  [Почтовое API](../app/api/email/router.py) ·
  [Узел чтения](../app/agent/nodes/read_and_retrieve.py) ·
  [RAG-индексация](../app/services/rag/ingestion/service.py)
- В репозитории есть FastAPI и Swagger, код отдельного фронтенда
  отсутствует. Здесь нужно реализовать API и задокументировать
  сценарий UI. API запускает миграции на старте. Текущий head —
  `001_gmail_schema`, рассчитанный на пустую локальную БД.
  [Сборка API](../app/main.py) ·
  [Миграция](../alembic/versions/001_gmail_schema.py)

## Схема хранения

Проект в разработке. Схему можно собрать с нуля на пустой БД,
переписав цепочку Alembic под актуальные модели. Существующие данные
для этой интеграции переносить не требуется. В новой схеме все письма
и треды принадлежат Gmail-аккаунту.

| Таблица | Изменения |
| --- | --- |
| `gmail_accounts` | `id UUID`, `owner_id → users.id`, отображаемое `name`, подтверждённый `gmail_email` после OAuth, `created_at`, `updated_at`. Индекс по владельцу. Уникальность подтверждённого адреса в пределах одного владельца. |
| `gmail_connections` | Связь 0..1 с аккаунтом через уникальный `gmail_account_id`. Поля OAuth `client_id`, зашифрованные `client_secret` и `refresh_token`, выданные scopes. Поля синхронизации `synced_through_at` (граница завершённого поиска в UTC), `status`, `next_sync_at`, `last_success_at`. Для воркера — токен и срок аренды, поколение подключения. Отдельные поля для подготовленных параметров OAuth и одноразовой попытки. |
| `threads` | `gmail_account_id → gmail_accounts.id` и `gmail_thread_id` обязательны (`NOT NULL`). Уникальность пары `(gmail_account_id, gmail_thread_id)`. Уникальность пары `(id, gmail_account_id)` для составного FK писем. |
| `raw_emails` | `gmail_account_id` и `gmail_message_id` обязательны (`NOT NULL`). Уникальность пары `(gmail_account_id, gmail_message_id)`. Составной FK `(thread_id, gmail_account_id) → threads(id, gmail_account_id)` гарантирует, что письмо и тред принадлежат одному аккаунту. |

UUID используются в HTTP и прикладных сервисах, Gmail ID — только в
импорте. Удаление или перенос аккаунта между пользователями через API
в MVP не предусмотрены. Для отключения и удаления данных определить
разные операции. При отключении остановить синхронизацию и скрыть
импортированную почту. Отдельная очистка должна удалять копии и
производные данные по аккаунту до удаления его записи. Срок хранения
отключённого импорта согласовать перед запуском.

## Подключение аккаунта и контракт фронта

| Метод под `/api/v1` | Действие |
| --- | --- |
| `POST /gmail/accounts` | Создать аккаунт по имени. Владелец берётся из текущей сессии. |
| `GET /gmail/accounts` | Вернуть аккаунты владельца с Gmail-адресом и статусом. |
| `PUT /gmail/accounts/{id}/connection` | Записать OAuth Client ID и Client Secret через HTTPS, для действующего подключения подготовить переподключение. |
| `POST /gmail/accounts/{id}/oauth/start` | Вернуть URL Google для авторизации и создать краткоживущую попытку. |
| `GET /gmail/oauth/callback` | Проверить попытку, принять код, обменять его на токены и вернуть пользователя на настроенный экран фронта. |
| `DELETE /gmail/accounts/{id}/connection` | Отключить локальную синхронизацию, очистить токены и снять открытые OAuth-попытки. |

Для запуска API заполнить `GMAIL_OAUTH_REDIRECT_URI`,
`GMAIL_FRONTEND_URL` и `GMAIL_ENCRYPTION_KEY` по `.env.example`.
Ключ Fernet можно сгенерировать командой
`uv run --locked python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`.
Зарегистрировать тот же callback URL в Google Cloud. Фронт вызывает
`oauth/start` с `credentials: "include"` и перенаправляет браузер на
`authorization_url`. Фронт и API должны быть на одном сайте,
например `localhost` на двух портах. После возврата с параметром
`gmail=connected` или `gmail=authorization_failed` фронт обновляет
список аккаунтов. На прокси отключить логирование query string для
OAuth callback.

1. Менеджер создаёт OAuth-клиент типа Web application в Google Cloud,
   включает Gmail API и регистрирует точный callback URL сервиса.
   Во фронте вводит Client ID и Client Secret, затем нажимает
   «Подключить Gmail». Пароль Gmail и refresh token в форме
   не запрашиваются. Redirect URI задаётся сервером.
2. Бэкенд запрашивает `gmail.readonly` и `access_type=offline`.
   OAuth `state` одноразовый, с TTL и серверной привязкой к
   владельцу, аккаунту, OAuth-клиенту и браузеру. Для браузера
   использовать краткоживущую cookie Secure, HttpOnly, SameSite=Lax.
   Попытка хранится в БД, чтобы callback переживал рестарт API.
   Callback принимает Google-редирект без Bearer-токена сервиса и
   атомарно погашает попытку. Коды и токены не попадают в URL фронта.
3. Бэкенд вызывает `users.getProfile('me')` и сохраняет адрес,
   подтверждённый Gmail. Проверяет наличие нужного scope и refresh
   token перед активацией. При повторном согласии сохраняет прежний
   refresh token только после подтверждения того же ящика и клиента.
   Если новый токен нужен, а Google его не выдал, UI запускает
   повторное согласие. Смена ящика требует отдельного аккаунта.
   Старое подключение заменяется только после успешного callback.
4. Воркеры обновляют access token через refresh token. Access token
   можно держать в памяти до истечения. Client Secret, refresh token
   и временные OAuth-секреты шифруются ключом вне БД. Из HTTP-ответов,
   логов, трассировки и логов callback исключаются секреты и код.
   Локальное отключение удаляет доступ у приложения. Интерфейс
   объясняет, как отозвать согласие в Google, если это требуется.
5. Фронт повторно читает `GET /gmail/accounts` после OAuth.
   Состояния для UI — ожидает подключения, синхронизируется, подключён,
   `Sync Error`, `Re-auth required`, отключён.
   Запросы к чужому ID отвечают 404. Роль admin сама по себе не даёт
   права читать чужой Gmail.

Для тестового Google-проекта с типом External и статусом Testing
refresh token с Gmail scope обычно истекает через семь дней.
`gmail.readonly` — restricted scope. Перед подключением реальной
почты проверить требования Google к верификации и оценке безопасности
для выбранного типа публикации и серверного хранения, а также описать
пользователю использование и хранение данных.
[Серверный OAuth](https://developers.google.com/workspace/gmail/api/auth/web-server) ·
[Жизненный цикл токенов](https://developers.google.com/identity/protocols/oauth2) ·
[Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes) ·
[Политика данных Google Workspace](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)

## Синхронизация писем и тредов

### Первый импорт за месяц

1. Зафиксировать верхнюю границу поиска в UTC на момент начала
   прохода и задать нижнюю на 30 суток раньше. Через
   `users.messages.list(q="after:<unix_seconds> before:<unix_seconds>")`
   пройти все страницы писем в этом интервале. Передавать Unix-время
   в секундах для точных границ и исключать Gmail-черновики, спам
   и корзину.
2. Собрать уникальные `threadId` и загрузить каждый тред целиком
   через `users.threads.get(format=full)`. Если в интервал попало
   хотя бы одно допустимое письмо, сохранить все допустимые письма
   цепочки, включая письма старше 30 суток. Эти письма сохраняются
   и для треда из одного сообщения. Проверять `labelIds` каждого
   письма и исключать `DRAFT`, `SPAM`, `TRASH`.
3. Записать тред и его письма по внешним ключам в одной короткой
   транзакции. После обработки всех страниц и записей сохранить
   верхнюю границу в `synced_through_at`, в том числе для пустого
   ящика. При сбое сохранить прежнюю отметку и повторить проход.
   Если Gmail вернул 404 для исчезнувшей цепочки, её можно пропустить.

[Поиск по дате](https://developers.google.com/workspace/gmail/api/guides/filtering) ·
[Список писем](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) ·
[Получение треда](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.threads/get) ·
[Квоты](https://developers.google.com/workspace/gmail/api/reference/quota)

### Последующий поиск новых писем

1. Искать по тому же Gmail-запросу от `synced_through_at` с
   небольшим перекрытием, например на пять минут, до начала нового
   прохода. Повторяющиеся письма отсекаются по Gmail ID в пределах
   аккаунта. Для новых писем загружать полные цепочки и делать
   идемпотентный upsert. Gmail-метки не меняют `Thread.status`.
2. Продвигать отметку только после успешной обработки всех страниц.
   `MAX(raw_emails.date)` служит датой самого свежего сохранённого
   письма, но для курсора важна граница завершённого поиска. Например,
   если самая новая запись уже сохранена, а следующая страница
   завершилась ошибкой, поиск от максимальной даты пропустит
   необработанные более ранние письма. Перекрытие также покрывает
   совпадения на границе и небольшую задержку появления письма
   в поиске.
3. Поиск по времени доставляет новые письма в рамках окна опроса.
   Изменения меток и удаление уже сохранённых писем сами по себе
   не запускают обновление. Письмо, добавленное в Gmail с датой
   старше окна поиска, тоже может быть пропущено. Если понадобится
   отслеживать эти события, перейти на `users.history.list`.
   [История изменений Gmail](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list)

### Нормализация

- Дата берётся из `internalDate` в миллисекундах и приводится к UTC.
  Отправителя, получателей и тему разбирать из MIME-заголовков
  штатными средствами Python. Для обязательного поля `recipient`
  сохранять первый подходящий адрес из `To` или согласованный
  fallback, например адрес подключённого ящика. Отдельно зафиксировать
  случаи Bcc и отсутствующих или некорректных заголовков.
- Обходить MIME-части рекурсивно, декодировать base64url и charset.
  У `multipart/alternative` брать `text/plain` либо преобразовывать
  HTML в обычный текст без загрузки внешних ресурсов. Не подмешивать
  файлы в тело письма. Часть с основным текстом, которую Gmail вынес
  в `attachmentId`, при необходимости получать с ограничением
  размера. Для повреждённого письма сохранить доступные безопасные
  метаданные и диагностический код. Сетевой сбой повторять как
  временный.
- Для темы треда брать тему первого доступного письма, для
  `client_email` — адрес внешнего участника, выбранного
  детерминированно по направлению письма. Проверить пустые и
  многополучательные сообщения на совместимость с текущим API.
  Для Gmail-метаданных и DTO использовать типизированные модели.
  [Ресурс Message](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages)

## Воркер и изоляция данных

Для локального запуска включить профиль Gmail в том же Compose-проекте,
где работает API:

```powershell
docker compose --profile gmail up -d --build gmail_worker
docker compose --profile gmail logs -f gmail_worker
```

Воркер использует `GMAIL_ENCRYPTION_KEY` из окружения API. По умолчанию
успешные проходы разделены минутой. Интервал задаёт
`GMAIL_SYNC_INTERVAL_SECONDS`. После первого прохода у аккаунта в
`GET /api/v1/gmail/accounts` появится `last_success_at`, а письма
можно найти через `GET /api/v1/emails/search` от имени владельца.

- Добавить `../app/workers/gmail_sync.py` и сервис в Compose.
  Воркера запускать после применения схемы, используя существующий
  запуск миграций API и проверку готовности. Воркер периодически
  забирает подключения с наступившим `next_sync_at`, например
  раз в минуту, и не требует RabbitMQ для опроса.
- Захватить подключение короткой транзакцией через
  `FOR UPDATE SKIP LOCKED`, записать аренду, завершить транзакцию
  до сетевых запросов. Обновлять аренду на длинном проходе.
  При записи очередной порции и курсора проверять токен аренды,
  поколение и статус под блокировкой строки подключения. Новое
  поколение при переподключении или отключении отклоняет записи
  уже запущенного прохода. После падения аренда истекает.
- При 401 однократно обновить access token и повторить запрос.
  Если Google отклонил refresh token с `invalid_grant` или для
  нужного scope требуется новое согласие, выставить `Re-auth required`
  и остановить опрос до успешного переподключения. При остальных
  ошибках прохода выставить `Sync Error` и назначить следующую
  попытку через `next_sync_at`, учитывая `Retry-After`, если он
  есть, иначе используя фиксированную задержку с jitter. После
  успешного прохода выставить статус «подключён». Метрики —
  отставание, число импортированных писем, ошибки и длительность
  проходов.
  Pub/Sub `watch` можно рассмотреть отдельно при переходе на
  синхронизацию по истории Gmail.
  [Квоты](https://developers.google.com/workspace/gmail/api/reference/quota) ·
  [Push-уведомления](https://developers.google.com/workspace/gmail/api/guides/push)
- Для HTTP-поиска и чтения добавить типизированную область доступа.
  SQL-фильтр разрешает чтение только владельцу аккаунта
  с действующим подключением, включая временный сбой опроса.
  Проверку применять до поиска, сортировки и LIMIT, включая поиск
  по внутреннему UUID. UI должен экранировать тему и тело, а
  подсветку результатов формировать безопасно.
- Gmail-письма доступны агенту и инструменту `create_draft` с проверкой
  владельца на всех путях. RAG-воркер индексирует письма после
  настраиваемой задержки. Основной сценарий описан в
  [плане почтового RAG](email_rag_implementation_plan.md).

## Порядок реализации и критерии приёмки

1. **База и доступ.** Обновить модели и репозитории, пересобрать
   цепочку Alembic и проверить `alembic upgrade head` на пустой БД.
   Обновить сидинг и тестовые фикстуры под обязательную связь с
   Gmail-аккаунтом. Тестовые ID использовать в тестовых данных.
   До включения воркера добавить фильтры чтения и запреты для
   агента, черновиков и RAG.
2. **OAuth и HTTP.** Добавить `app/api/gmail/`, сервис управления
   аккаунтом, настройки и async-клиенты OAuth и Gmail на
   существующем `httpx`. Описать OpenAPI, callback и статусы для
   фронта. Проверить создание аккаунта, 404 на чужой ID, state
   с истёкшим TTL и повторным использованием, подмену ящика и
   отзыв доступа. Секреты не видны в ответах и логах.
3. **Импорт.** Добавить сервис синхронизации и MIME-маппинг,
   пакетный upsert, полнотекстовое чтение и отметку поиска.
   Проверить пагинацию, пустой ящик, тред с письмами по обе стороны
   30-дневной границы, старый тред без свежих писем, письмо во
   время импорта, одинаковое время у двух писем и сбой после
   частичной записи. Повтор прохода не создаёт дубликаты писем
   и тредов.
4. **Эксплуатация.** Добавить воркер, аренду, статусы, расписание
   и повторные попытки. Проверить два конкурирующих воркера,
   отключение во время запроса, перезапуск после частичной записи,
   rate limit и истёкший refresh token. Запустить `uv run --locked
   python -m pytest` и выполнить сквозной сценарий на тестовом
   Google-аккаунте. Приёмка включает отрицательную проверку
   поиска и чтения Gmail-писем из сессии второго менеджера.
